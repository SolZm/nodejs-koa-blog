# AI 站内问答（RAG）

## 一、它是什么

读者在博客上提问 → 系统在文章切片里检索 → 把检索到的原文作为资料交给模型 →
流式返回回答。回答采用混合知识模式：

- **博客资料**：来自检索到的文章，事实性内容带 `[编号]`，可回查原文。
- **延伸说明**：模型使用稳定的通用技术知识补充原理、例子、对比、场景和取舍，不伪造博客引用。

博客没有直接命中时不会整次拒答，而是明确告诉读者“博客中没有直接相关内容”，随后继续给出通用技术说明。

```
问题 → 切片(article_chunk) → 关键词路 + 向量路 → RRF 融合 → 置信度判断
      → 拼 prompt（博客资料 + 通用补充约束）→ 流式生成 → 回答 + 引用链接
```

## 二、接口

### POST /api/v1/ai/ask

公开接口，按 IP 限流 10 次/分钟（全局那条约 100 次/分钟，这里单独收紧，因为每次都要调模型）。

请求：

```json
{ "question": "LangGraph 测试怎么写" }
```

响应：`text/event-stream`，逐条推送

```
event: meta
data: {"knowledge_mode":"hybrid","blog_hit":true}

event: delta
data: {"text":"片段"}

event: citations
data: {"citations":[{"index":1,"article_id":31,"title":"LangGraph 测试三大层级","headings":["一、整图测试","三、部分执行测试"]}]}

event: done
data: {"latency_ms":487,"cached":false,"knowledge_mode":"hybrid","blog_hit":true}

event: error
data: {"msg":"...","errorCode":10000}
```

`blog_hit=false` 表示本轮没有采用博客文章作为资料，回答会以通用技术说明为主，`citations` 为空。

**编号按来源（文章）给，不按切片给。**

检索是按切片排序的，一篇文章匹配度高时会有多个切片同时入选——这对回答是好事
（模型需要同篇文章的多个段落才能答完整）。但如果按切片编号，同一篇文章就会占掉
`[1][2][3]` 好几个号，读者以为有好几份来源，而引用列表里只有一篇，看起来就对不上。

所以上下文按文章重组：一篇文章 = 一份资料 = 一个编号。`headings` 是这份来源里
被用到的章节，供读者定位。

### POST /api/v1/ai/reindex

管理员接口（需要 ADMIN 权限）。重建索引。

```json
{ "force": false, "id": 31 }
```

`force` 省略则走增量，`id` 省略则处理全部。响应：

```json
{ "code":200, "data": { "processed":0, "skipped":31, "failed":0, "chunks":0, "seconds":0.1 } }
```

### GET /api/v1/ai/stats?days=7

管理员接口。返回博客命中率、博客未命中率、缓存命中率、平均延迟、token 用量，以及按天聚合。

注意：混合知识模式下，博客未命中不等于没有回答。`no_result_rate` 现在表示“没有采用博客资料的比例”。

## 三、环境变量


| 变量                 | 说明                                                         |
| -------------------- | ------------------------------------------------------------ |
| `AI_PROVIDER`        | `mock`（本地、不联网、不花钱）或 `openai`（OpenAI 兼容协议） |
| `AI_BASE_URL`        | 如`https://dashscope.aliyuncs.com/compatible-mode/v1`        |
| `AI_API_KEY`         | 密钥，**不要写进代码**                                       |
| `AI_CHAT_MODEL`      | 对话模型名                                                   |
| `AI_EMBEDDING_MODEL` | 向量模型名                                                   |
| `AI_EMBEDDING_DIM`   | 向量维度，mock 模式用它决定长度                              |
| `AI_MIN_RELEVANCE`   | 博客资料阈值，不填按 provider 取默认（mock 0.14 / openai 0.6） |

## 四、nginx 需要加什么

流式接口必须关掉响应缓冲，否则前端会「卡很久然后一次性全出来」，打字机效果失效。
在 API 那个 `server` 块里：

```nginx
location /api/v1/ai/ {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;

    # 关键：不缓冲，边生成边推送
    proxy_buffering off;
    proxy_cache off;
    chunked_transfer_encoding on;

    # 模型生成可能比较慢，读超时给足
    proxy_read_timeout 300s;
    proxy_send_timeout 300s;
}
```

代码里已经带了 `X-Accel-Buffering: no` 响应头，但显式配 `proxy_buffering off` 更稳妥。

## 五、本地怎么跑

```bash
# 1. 建表（会创建 article_chunk / ai_query_log / 全文索引）
npm run migrate

# 2. 建索引：切片 + 向量化 + 入库
npm run index              # 增量，只处理新增或内容有变化的文章
npm run index -- --force   # 全量重建
npm run index -- --id=31   # 只处理一篇，方便调试

# 3. 起服务
npm run dev
```

`AI_PROVIDER=mock` 时不需要任何 key：它用字符二元组哈希生成「伪向量」，
虽然没有语义能力，但字面越接近向量越相似，足以把整条链路跑通并做检索验证。

## 六、检索是怎么做的

**两路召回，RRF 融合。**

- 关键词路：MySQL 全文索引（`WITH PARSER ngram`，中文必须用它，否则按空格切词等于废掉）
- 向量路：问题向量化后与全部切片算余弦相似度

为什么必须混合：纯向量对 `MCP`、`SSE`、`DIP` 这种缩写和专有名词召回差，
关键词路几乎是精确命中；反过来关键词对同义改写无能为力，那是向量路的强项。

融合用 RRF（`score = Σ 1/(k + rank)`，k=60），只看排名不看分数，
因此不需要把两个不同量纲的分数归一化，最省心。

**博客资料阈值。** 两路召回几乎总能捞回一些东西，不设阈值的话，
无关文章也会被当成来源塞进上下文。所以加了 `AI_MIN_RELEVANCE`：
置信度低于它时，本轮不采用博客资料，但混合知识模式仍会继续生成通用技术说明。

这个值是用数据选的，不是拍脑袋：`npm run eval -- --scan` 会在 22 道正样本 + 8 道负样本上扫描阈值，
输出「博客召回 vs 无关来源过滤」的权衡曲线。mock 模式下实测：

**这个值必须按模型重新标定，实测差别极大。**

用 mock（字符重叠）扫出来是 0.14；换成真实模型 `text-embedding-v3` 后，
置信度分布整体抬高（正样本 0.614~0.884，负样本 0.362~0.645），
原来的 0.14 **无关问题过滤率是 0%**——等于完全失效。重新扫描后：


| 阈值     | Hit@3      | 博客漏命中率 | 正确过滤率 |
| -------- | ---------- | -------- | ---------- |
| 0.45     | 100.0%     | 0.0%     | 37.5%      |
| 0.50     | 100.0%     | 0.0%     | 62.5%      |
| 0.55     | 100.0%     | 0.0%     | 87.5%      |
| **0.60** | **100.0%** | **0.0%** | **87.5%**  |

拐点在 0.60：再往上就会开始误伤正样本（正样本最低置信度 0.614）。
阈值现在只决定“要不要把文章作为博客资料”，不会阻止通用技术说明。
因此它主要影响引用质量和上下文 Token，不再决定整次问答是否拒答。

**换成真实模型后分布完全不同，必须重新跑一次 `--scan` 重新选值**——这也是为什么它是配置项而不是常量。

## 八、评测

```bash
npm run eval                  # 三种模式对比：纯关键词 / 纯向量 / 混合
npm run eval -- --verbose     # 逐题详情，用来定位是哪道题拖后腿
npm run eval -- --scan        # 扫描博客资料阈值，输出权衡曲线
```

指标口径：先取回 10 个切片 → **按文章去重**（否则一篇长文章会霸榜，指标虚高）→ 考察前 3 个来源。

- `Hit@3`：期望文章出现在前 3 个来源里的比例
- `MRR`：第一个正确来源排名的倒数平均值

评测集分正负两组是有意的：只测召回，你会不自觉把阈值调低（什么文章都引用，命中率自然好看）；
只测无关问题过滤，又会把阈值调高（什么来源都不要，准确率满分但系统没用）。**必须两组一起看。**

> mock 模式的向量是字符重叠算出来的，数字只说明管道通了，不代表真实语义检索效果。
> 接入真实模型后必须重跑，并重新扫描阈值。

## 九、日志切割

PM2 日志不切割会一直涨，几个月就能把磁盘吃满。在服务器上装一次：

```bash
pm2 install pm2-logrotate
pm2 set pm2-logrotate:max_size 10M
pm2 set pm2-logrotate:retain 7
pm2 set pm2-logrotate:compress true
```

`max_size` 是单文件上限，`retain 7` 是保留 7 份，`compress` 开启压缩。
装完用 `pm2 list` 能看到多出一个 `pm2-logrotate` 进程。

## 十、真实模型实测记录

下面是接百炼（`text-embedding-v3` + `qwen-plus`）实测的一组数据，留档用来做对照——
下次换模型或改检索逻辑时，拿它当基线。

### 检索质量：mock 和真实模型给出的结论完全不同


| 模式    | mock 向量 | `text-embedding-v3` |
| ------- | --------- | ------------------- |
| keyword | 69.6%     | 69.6%               |
| vector  | 77.3%     | **95.7%**           |
| hybrid  | 77.3%     | 95.7%               |

mock 模式下向量路几乎不比关键词强，混合看着毫无价值；
换成真实语义模型后差距立刻拉开。**这说明「混合检索到底有没有用」这个问题，
在本地假向量上是问不出答案的**——如果只看 mock 的数字就下结论，会得出完全错误的判断。

### 博客资料阈值：必须跟着模型重标

同一个系统，只换了向量模型，最优阈值从 **0.14 变成 0.60**：


|                  | mock        | text-embedding-v3               |
| ---------------- | ----------- | ------------------------------- |
| 正样本置信度范围 | 0.18 ~ 0.61 | 0.614 ~ 0.884                   |
| 负样本置信度范围 | 0.06 ~ 0.18 | 0.362 ~ 0.645                   |
| mock 时定的 0.14 | 正常工作    | **无关问题过滤率 0%（等于失效）** |
| 重新标定的 0.60  | —          | Hit@3 95.7%、零漏命中、过滤 87.5% |

原因很直观：真实模型的余弦相似度整体抬高，不同模型的分布尺度不一样。
所以阈值只能是「跑一遍 `--scan` 选出来」，不能是「参考某个值填进去」。

### 对话模型延迟（同一个问题，各测一次）


| 模型                | 耗时    | 回答长度 |
| ------------------- | ------- | -------- |
| `qwen3.5-122b-a10b` | 9307 ms | 183 字   |
| `qwen-plus`         | 4001 ms | 258 字   |
| `qwen-turbo`        | 1479 ms | 224 字   |

122b 的 MoE 模型对博客问答属于杀鸡用牛刀，默认选 `qwen-plus`；
对延迟更敏感的场景可以直接换 `qwen-turbo`。

### 已知失败用例

> 「怎么让多个组件之间松耦合地通信？」期望命中《发布订阅模式（EventBus）解耦网络模块和路由模块》，
> 实际召回了 MCP 进程通信那篇，最终被阈值过滤，没有采用为博客资料。

推测原因是问法里的「通信」把向量拉向了 MCP 那篇（它整篇在讲进程通信），
而目标文章用的是「解耦 / 网络模块 / 路由模块」这类词。

## 七、已知取舍与边界


| 事项         | 现状                                                  | 什么时候需要改                           |
| ------------ | ----------------------------------------------------- | ---------------------------------------- |
| 向量检索方式 | 全量扫描 + 内存缓存（5 分钟 TTL），300 多条切片毫秒级 | 上万条切片时换 pgvector / Milvus         |
| 超长切片     | 整块代码不切，最长约 4KB（占 12.4%）                  | 若评测显示命中率受影响，可加硬上限按行切 |
| 答案缓存     | 进程内 Map，10 分钟 TTL，最多 200 条                  | 多实例部署时要换成 Redis                 |
| 建索引       | 离线脚本或管理员接口，串行处理                        | 文章规模大了要改成并发 + 断点续跑        |
| 博客资料阈值 | mock 0.14 / openai 0.6                                | 换模型后必须用评测集重新标定             |
