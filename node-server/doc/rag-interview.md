# 站内 RAG 问答 —— 面试知识点总结

> 这份文档整理自我给自己博客做的「问博客」功能（前端 + 后端）。
> 结构是：**业务场景 → 为什么这么设计 → 用了什么知识点 → 实测数据 → 踩过的坑**。
> 面试时最有价值的不是"我用了什么技术"，而是**每个决策背后的权衡和证据**，所以我把实测数字都留下了。
>
> **2026-10-17 更新**：在线问答已经升级为“博客资料 + 通用技术补充”的混合模式。
> 博客内容仍强制引用；通用知识放在独立的“延伸说明”中，不伪造引用；博客没有命中时也不会整次拒答。
> 下文关于严格 RAG、拒答阈值与早期 prompt 的内容，保留为设计演进的上下文。

---

## 一、业务场景：为什么要做这个

### 现状

我的博客有 31 篇技术文章，集中在**前端工程**（Vue / 构建工具 / 设计模式）和 **AI 应用**（RAG / MCP / LangGraph / Agent）两个方向。

### 读者的真实困境

文章写多了以后，两种搜索都不好用：

| 场景 | 问题 |
|---|---|
| 读者记得"某篇里讲过方法"，但不确定是哪篇 | 只能一页页翻 |
| 读者用**自己的说法**搜 | 关键词搜不到。比如想找「怎么让请求不重复」，但文章标题是《Axios封装-取消重复请求》 |
| 读者用**太宽泛的词**搜 | 比如搜 "MCP"，命中一堆，但不知道哪段能回答他的具体问题 |

### 目标

让读者**用自然语言提问**，系统在我自己的文章里检索出相关段落，交给大模型**基于原文**回答，并给出**可核查的引用出处**。

### 为什么这件事值得做（业务价值）

1. **对读者**：不用翻文章，直接问；答案带引用，可信、可核查
2. **对我**：内容二次消费（文章的价值被放大），而且提问记录能反向告诉我"哪些主题写得不够清楚"
3. **对系统**：它是纯增量的——不影响原有文章、评论、后台任何功能

### 关键约束（这几条直接决定了技术选型）

| 约束 | 推导出的决策 |
|---|---|
| 只有 31 篇文章、331 个切片 | **不上向量数据库**，MySQL + 内存暴力计算就够了 |
| 单人维护、成本敏感 | 离线建索引、答案缓存、接口限流 |
| 已有栈是 Node(Koa2) + MySQL + Nuxt 2 | 尽量不引入新组件，用现有栈解决 |
| 回答既要有深度，又要可核查 | 博客事实强制引用；通用知识单独标注；两者不混用 |

## 二、整体架构

```
【离线】一次性/增量执行
  文章(Markdown)
    → 按标题层级切片          ① 切片策略
    → 向量化（text-embedding-v3）② 向量化
    → 写入 article_chunk      ③ 数据层

【在线】每次提问
  问题
    → 关键词召回（MySQL ngram 全文索引）┐
    → 向量召回（余弦相似度暴力扫描）    ┘ ④ 混合检索
    → RRF 融合
    → 置信度判断（低于阈值就不采用博客资料）⑤ 资料阈值
    → 拼 prompt（博客引用 + 通用补充分层）  ⑥ 生成层
    → 流式返回（SSE）                   ⑦ 接口
    → 前端打字机渲染 + 引用卡片         ⑧ 前端
```

后端分层沿用我原有的约定：`路由 → controller → service → dao`。
新增代码在 `app/service/ai/` 下，按职责拆成 `chunk / embedding / retrieval / chat / qa / indexer`。

## 三、后端知识点

### ① 切片策略：为什么按标题切，而不是按固定长度

**核心判断：技术文章的结构本身就是语义单元。**

一段内容"在讲什么"，由它所在的章节决定。按 500 字硬切，会把「核心思路」和「代码示例」混进同一块，检索出来答非所问。

具体做法：

1. **按 Markdown 标题层级切**（`##` / `###`），维护标题路径（如 `一、整图测试 > 核心思路`）
2. **代码块必须整体保留** —— 实现上要先扫围栏（```），否则代码里的 `# 注释` 会被误当标题，把一块完整代码从中间劈开
3. 过长的段按段落拆（上限 800 字）；过短的块前后合并（下限 100 字），避免产生"碎片块"
4. 相邻切片加 50 字重叠，防止一句话正好被切在边界上

**实测数据**（31 篇文章）：

| 指标 | 数值 |
|---|---|
| 切片总数 | 331 |
| 平均每篇 | 10.7 片 |
| 长度 中位 / p90 | 368 / 835 字 |
| 低于下限（碎片） | 4 片（1.2%） |
| 超过上限 | 41 片（12.4%） |

> **这里有个要主动说的取舍**：12.4% 的切片超过 800 字上限，因为我**故意不切代码块**。
> 一个 4KB 的完整代码示例，对「LangGraph 测试怎么写」这类问题，比切成两个半截示例更有用。
> 这是取舍不是 bug，而且数字是可测的——真要调，加个硬上限按行切即可。

### ② 向量化：为什么要做 mock 模式

**问题**：接真实模型要花钱、要联网、要 key。在没有 key 的时候，怎么验证"整条链路是通的"？

**做法**：实现一个 `AI_PROVIDER=mock` 模式——把字符二元组哈希到固定维度（hashing trick），再 L2 归一化。

它**没有语义能力**，但字面越接近、向量越相似，所以：

- 能验证「建表 → 切片 → 向量化 → 入库 → 检索 → 接口 → 评测」整条链路
- **不花钱、不联网**，写测试也不依赖外部服务
- 实测 mock 向量也能正确检索：4 个测试问题全部命中正确文章

**另一个设计点：走 OpenAI 兼容协议。**
`POST {AI_BASE_URL}/embeddings` 和 `/chat/completions`，换厂商（百炼 / DeepSeek / OpenAI）只改环境变量，代码一行不动。

工程细节：批量（10 条/次）+ 重试（3 次）+ 超时（AbortController）。

### ③ 数据层：几个刻意的设计

`article_chunk` 表：

| 字段 | 为什么需要 |
|---|---|
| `heading_path` | 让读者知道引用出自哪一节，也让模型有上下文 |
| `content_hash` | **增量索引**：内容没变就不重新向量化 |
| `embedding_model` | **换模型时自动识别**：比对模型名不同就全量重建 |
| `char_len` | 诊断切片是否合理（上面那些统计就是靠它算的） |
| `embedding` (JSON) | 300 多条切片只有几 MB，JSON 够用且好调试，不需要二进制或向量库 |

**为什么这两张表不做软删除**：它们是派生数据（重建时物理删掉重写）和追加型日志。留 `deleted_at` 只会让表越来越大，还得每次查询都过滤。

### ④ 混合检索：为什么不能只用向量

**两路召回：**

| 路径 | 实现 | 强项 | 弱项 |
|---|---|---|---|
| 关键词 | MySQL 全文索引，`WITH PARSER ngram` | 专有名词、缩写精确命中 | 同义改写没辙 |
| 向量 | 问题向量化后与所有切片算余弦 | 同义改写、语义相近 | 缩写/专有名词召回差 |

**为什么中文必须用 ngram**：MySQL 默认全文分词按空格切，对中文等于废掉（一整句话变成一个大词）。ngram 按 2 字一组切，中文才有召回能力。

**融合用 RRF（Reciprocal Rank Fusion）**：`score = Σ 1/(k + rank)`，k=60。
选它的理由是**工程上最省心**：两路的分数不可比（全文检索给的是相关度、余弦给的是相似度），RRF 只看"排第几名"，因此不需要任何归一化调参。

**为什么用暴力扫描而不是向量库**：331 个切片全量算余弦只要几毫秒，上向量数据库反而引入一个要运维的组件。加了 5 分钟 TTL 的内存缓存，避免每次请求都重新读表 + JSON 解析。

> **知道边界在哪**：上万条切片时全量扫描就不行了，那时候再换 pgvector / Milvus。

### ⑤ 博客资料阈值：这个功能最有故事的部分

**为什么必须有阈值**：两路召回几乎总能捞回一些东西。不设阈值的话，无关文章也会被当作博客资料塞进上下文，污染引用和回答。

**我是怎么标定它的（这段是面试重点）：**

1. 一开始只用短查询测，量出 mock 模式下正样本最低 0.180、负样本最高 0.178，取了 **0.18**
2. 建了评测集（22 道正样本 + 8 道负样本）后发现问题：**向量路在 4 道本该能回答的问题上返回了空结果**——比如「MCP 是什么？它解决什么问题？」，因为句子长、字符重叠天然更低，被 0.18 误拒了
3. 根因是**我只测了召回、没测无关来源过滤**。补上负样本和阈值扫描后，做成一条命令：`npm run eval -- --scan`

**阈值扫描的原理**：先把阈值设为 0 跑一轮检索，拿到「原始候选 + 置信度」，再在本地对这份数据做不同阈值的一刀切——**避免每换一个阈值就重新调一次向量服务**（6 个阈值 × 30 道题 = 180 次 API 调用）。

**真实模型下的扫描结果**：

| 阈值 | Hit@3 | 博客漏命中率 | 正确过滤率 |
|---|---|---|---|
| 0.45 | 100.0% | 0.0% | 37.5% |
| 0.50 | 100.0% | 0.0% | 62.5% |
| **0.60** | **100.0%** | **0.0%** | **87.5%** |

**这里有个必须讲清楚的结论：阈值必须跟着模型重新标定。**
同一个系统只换了向量模型，最优阈值从 **0.14 变成 0.60**——mock 的 0.14 在真实模型下过滤率是 **0%**（完全失效）。因为不同模型的余弦相似度分布尺度不一样。

所以它是**配置项，不是常量**。

**升级为混合知识模式后**，阈值只决定“要不要把文章当作博客资料”，不会阻止通用技术说明。
因此它主要影响引用质量和上下文 Token，不再决定整次问答是否拒答。

### ⑥ 生成层：博客引用与通用补充分层

```
1. 博客资料只转述检索到的原文，事实性内容用 [编号] 标注出处；
   编号只能取自资料编号，
   同一份资料无论引用几次都用同一个编号（不要自己造新编号、不要递增）
2. 通用技术知识放在“延伸说明”中，补充原理、例子、对比、场景和取舍；
   这里不得添加 [编号]，不能暗示内容来自博客
3. 博客资料只覆盖部分问题时，先回答已有部分，再继续延伸，不整体拒答
4. 博客没有直接命中时，明确说明，然后继续生成通用技术说明
```

第 2 条是踩坑后加的，见后面「七、踩过的坑」。

### ⑦ 接口层

**用 SSE 流式返回**，事件格式：

```
event: delta      data: {"text":"片段"}
event: citations  data: {"citations":[{"index":1,"article_id":26,"title":"…","headings":["…"]}]}
event: done       data: {"latency_ms":1234,"cached":false}
event: error      data: {"msg":"…","errorCode":10000}
```

几个刻意的设计：

| 设计 | 理由 |
|---|---|
| **单独限流 10 次/分钟** | 全局限流是 100/分钟，但问答每次都要调模型、按量计费，被刷的代价完全不同 |
| **答案缓存**（问题归一化后做 key，10 分钟 TTL） | 相同问题直接复用，省一次模型调用；实测第二次提问延迟归零 |
| **查询日志表** | 记问题、召回结果、置信度、耗时、token——用来算命中率、拒答率、成本 |
| **错误直接透传** `err.message` | 出问题时能一眼看到原因，而不是一句"服务器繁忙"。（实践中确实靠它快速定位了一个坑，见第七节） |
| `X-Accel-Buffering: no` | 让 nginx 不要缓冲流式响应 |

### ⑧ 工程化：为这个功能铺的地基

| 做了什么 | 为什么 |
|---|---|
| **配置外置到环境变量** | 密钥不再进代码；换环境不改代码 |
| **生产环境缺必需变量就 `process.exit(1)`** | 早失败：宁可启动不起来，也不要拿默认值悄悄跑在生产上 |
| **引入数据库迁移替代 `sequelize.sync()`** | `sync()` 只能加表加列，改列类型/删列/回滚都不行，更没法搬数据 |
| **确立 `route → controller → service → dao` 分层** | 业务逻辑可复用、可测试；RAG 的检索逻辑同时被接口和评测脚本调用 |
| **`.nvmrc` + `engines` + 运行时自检** | 声明"需要 Node 18"，避免报错指向不明 |

## 四、前端知识点

### ① SSE 客户端：为什么用 fetch 而不是 axios

SSE 是流式响应，浏览器端需要**逐段读取**。`fetch` 的 `response.body` 可以直接拿 reader：

```js
const reader = response.body.getReader()
while (true) {
  const { done, value } = await reader.read()
  if (done) break
  buffer += decoder.decode(value, { stream: true })
  // 用空行切事件，最后一段可能是半个事件，留到下一轮再拼
}
```

axios 在浏览器端不方便做这件事，所以这一层单独实现，但**返回值仍沿用项目的 `[err, res]` 约定**，保持风格统一。

### ② Markdown 渲染与 XSS 边界

模型的回答是 Markdown，必须渲染而不是当纯文本（否则 `###`、`**` 会原样显示）。

**这里必须想清楚安全边界**：用了 `v-html`，就必须确认渲染器会转义原始 HTML。项目的 `markdown-it` **没有开 `html` 选项（默认 false）**，源码里的 `<script>` 会被转义成文本——所以这个用法是安全的。这条依据写进了代码注释。

### ③ 引用编号高亮：为什么不正则替换 HTML

需求：让正文里的 `[1][2]` 显眼一点。

**不能这么做**：对渲染后的 HTML 做 `replace(/\[(\d+)\]/g, ...)`——代码块里的 `arr[1]`、`params[0]` 会被一起高亮。

**正确做法**：先 `md.parse()` 成 token，**只处理 `text` 类型的 token**，在里面插入 `html_inline`：

```
Markdown → token 流
  ├─ fence       ← 代码块，不动
  ├─ code_inline ← 行内代码，不动
  └─ text        ← 只有这里才是"正文"
```

代码块在**别的 token 类型**里，所以天然不会被碰到——不是靠正则去"排除"，而是**结构上就够不着**。

### ④ 引用卡片：按文章聚合

检索是按切片排序的，一篇匹配度高的文章会占掉好几个名额。如果按切片展示，底部会出现 6 张**同标题**的卡片，读起来像重复。

所以引用列表按**文章**聚合：一张卡片 + 涉及到的章节。

> 但这里踩了个坑：聚合后编号口径不一致了，见第七节。

### ⑤ 等待状态

真实模型首字节要 0.8~4 秒，必须有明确的等待反馈：

- 三段跳动的圆点 + 「正在检索并生成…」
- 发送按钮 loading、输入框禁用
- 尊重 `prefers-reduced-motion`（开了减少动画就静止）

### ⑥ Element UI 按需引入的坑

项目是**按需注册**组件的。我写了 `<el-input>` 但注册表里没有 `Input`，结果是：**Vue 不报错、直接不渲染**——按钮孤零零在那，输入框凭空消失。

定位方式：在浏览器里量元素的真实几何尺寸，发现 `.el-input` 根本不存在。

### ⑦ CSS 吸顶失效：sticky 的作用范围

`position: sticky` 写在元素上完全合法，但它**只能在自己的父元素范围内吸附**。

原来的 `.header` 父元素高度和它一样（72px），吸附空间是 0 —— 所以 `sticky` 写了等于没写。把吸附属性提到外层（父元素变成整个页面）才生效。

**这类问题看代码看不出来**，只有量"父元素给了多少吸附空间"才能定位。

## 五、实测数据（面试时最有说服力的部分）

### 检索质量：mock vs 真实模型

| 模式 | mock 向量 | `text-embedding-v3` |
|---|---|---|
| keyword | 69.6% | 69.6% |
| vector | 77.3% | **95.7%** |
| hybrid | 77.3% | 95.7% |

**这张表的重点不是数字，而是结论**：mock 模式下向量路几乎不比关键词强，混合看着毫无价值；换成真实语义模型后差距立刻拉开。
**"混合检索到底有没有用"这个问题，在本地假向量上是问不出答案的**——只看 mock 的数字会得出完全错误的判断。

### 向量服务的语义能力（同一组对比）

```
同义句相似度  0.81   （"Nginx 负载均衡的调度算法" vs "负载均衡有哪些算法"）
无关句相似度  0.35   （"Nginx 负载均衡的调度算法" vs "红烧肉怎么做才好吃"）
```

### 对话模型延迟（同一个问题）

| 模型 | 耗时 |
|---|---|
| `qwen3.5-122b-a10b` | 9307 ms |
| **`qwen-plus`** | **4001 ms** |
| `qwen-turbo` | 1479 ms |

122b 的 MoE 模型对博客问答属于杀鸡用牛刀，所以默认选 `qwen-plus`。

### 端到端

| 指标 | 数值 |
|---|---|
| 索引规模 | 31 篇 / 331 片，全量重建 17.7 秒 |
| 首字节到达 | 786 ms（说明流式没被 nginx 缓冲） |
| 整段回答 | 约 4.5 秒 |

## 六、面试可能被追问的问题（提前准备）

**Q：为什么不用 LangChain / LlamaIndex？**
> 这个规模用不上。整条链路（切片、向量化、RRF、prompt）我自己写了一遍，总共几百行，
> 出了问题能直接定位。引入框架反而多一层黑盒。等逻辑复杂到需要多步 Agent 编排时再考虑。

**Q：为什么不用向量数据库？**
> 331 条切片，全量算余弦几毫秒。上向量库要多一个要运维的组件（部署、备份、版本升级）。
> 我的判断标准是：**上万条切片时换 pgvector**，因为那时候全量扫描会变成性能瓶颈。

**Q：怎么保证回答不胡说？**
> 三层：① 博客引用只能指向本轮检索结果 ② prompt 把“博客资料”和“通用补充”拆开，通用知识不得伪造引用 ③ 所有引用都能点回原文核查。

**Q：怎么知道效果好不好？**
> 建了评测集：22 道正样本 + 8 道负样本，指标是 Hit@3 和 MRR，
> 而且**必须正负两组一起看**——只测召回会把阈值调低（什么都能答），只测拒答会把阈值调高（什么都拒答）。

**Q：如果文章涨到几千篇怎么办？**
> 三件事要改：① 向量检索从全量扫描换成 pgvector/Milvus ② 索引改成并发 + 断点续跑 ③ 答案缓存从进程内 Map 换成 Redis（多实例部署时）。
> 但切片策略、混合检索、引用约束这些都不用动——它们和规模无关。

## 七、踩过的坑（面试问"遇到什么困难"就用这些）

### 坑 1：编号口径不一致（最有价值的一个）

**现象**：回答里每句话后面都有编号 `[1] [2] [3] [5]`，看起来像引用了好几篇，但底部只列出一篇文章。

**根因**：**按切片编号，却按文章展示**。检索是按切片排序的，一篇匹配度高的文章占了好几个切片名额，于是产生了 `[1]`~`[6]` 六个编号，而来源只有一篇。

**修复**：在送进模型之前就**按文章重组上下文**——一篇一个资料块、一个编号，并在 prompt 里要求"同一份资料无论引用几次都用同一个编号"。

**结果**：编号数 = 来源数，永远对得上。
**意外收获**：改成来源编号后模型表现更好——它能明确搭出「资料 [1] 方案 / 资料 [2] 方案」的对照表。
**说明编号的语义从"碎片"变成"来源"后，模型对任务的理解也更清晰了。**

### 坑 2：`fetch is not defined`

**现象**：线上 AI 接口报 `fetch is not defined`，但本地和刚部署时都能用。

**定位**：`fetch` 是 Node 18 才有的全局 API。查 `pm2 describe app` 发现 `interpreter` 是裸命令 `node`，而那台机器上装了 **v12 / v16 / v18 三个版本**：

- 从 SSH 交互式 shell 启动 → PATH 解析到 nvm 的 v18 → 正常
- 从云效部署脚本启动（非交互式 shell，没加载 nvm）→ 解析到系统旧版本 → 没有 fetch

**修复**：① 部署脚本里用绝对路径指定解释器 `--interpreter /root/.nvm/.../bin/node` ② 代码里加运行时自检，把 `fetch is not defined` 换成一句能直接照着修的话。

**教训**：**用裸命令启动 = 把运行时版本交给 PATH 决定**。多版本环境里必须钉死。

### 坑 3：输入框凭空消失

**现象**：抽屉里只有发送按钮，输入框不见了，控制台无报错。

**根因**：Element UI 按需注册，注册表里没有 `Input`，`<el-input>` 是未注册组件 → 静默不渲染。

**定位方式**：在浏览器里量元素尺寸，`document.querySelector('.ask-input .el-input')` 返回 null。

**教训**：**"没报错"不等于"没问题"**——按需引入的组件缺失是静默失败的。

### 坑 4：代码块里的数组下标被误高亮

**现象**（在实现引用高亮时预见并规避）：如果用正则替换渲染后的 HTML，代码里的 `arr[1]` 会被当成引用编号。

**做法**：改成按 token 处理，只动 `text` 类型的 token，代码块结构上就够不着。

**教训**：**处理结构化文本时，走 AST/token 而不是正则**，让"不该动的东西"在结构上就接触不到。

### 坑 5：`position: sticky` 写了却不生效

**根因**：sticky 只能在**父元素范围内**吸附，而 `.header` 的父元素高度和它完全一样（吸附空间 0px）。

**教训**：这类问题**看代码看不出来**，必须量真实几何尺寸。

## 八、一句话总结这个项目

> 我给自己的技术博客做了一个站内问答：读者用自然语言提问，系统在 31 篇文章、331 个切片里做
> **关键词 + 向量双路召回**，用 RRF 融合，低于置信度阈值就不采用博客资料，
> 检索到的原文按**一篇文章一个编号**交给大模型；博客事实强制引用，通用技术补充独立成“延伸说明”，
> 最后用 SSE 流式返回。
>
> 最花时间的不是写功能，而是**建立评测**——22 道正样本 + 8 道负样本，
> 用 Hit@3/MRR 做消融对比，用阈值扫描选出最优博客资料阈值。
> 这个过程推翻了我两个凭直觉的判断：混合检索在 mock 下其实没赢，而阈值必须跟着模型重新标定（0.14 → 0.60）。
